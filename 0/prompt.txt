bool block_frame(const uint8_t *f, size_t n) {
    if (n &lt; 1) return false;
    uint8_t fc = f[0];
    uint8_t type = (fc &gt;&gt; 2) &amp; 0x3;

}

## `selectAttackHistory` grouping logic
`dashboard/src/dashboardView.ts:61-83`.

- Finds all indexes of `ANOMALY_DETECTED` lines in the (newest-first) timeline: `anomalyIndexes` (`dashboardView.ts:62`).
- For each anomaly, defines a **segment** from the previous anomaly (exclusive) up to and including this anomaly (`segmentStart` at `dashboardView.ts:65`), then filters that slice to lines with the **same `node_id`** as the anomaly (`dashboardView.ts:67-69`). So incidents are grouped by **anomaly boundaries + matching `node_id`**, not by any explicit incident id.
- `status`: first mapped `STATUS_BY_EVENT[line.type]` found in the segment, else "Devin processing" (`dashboardView.ts:27-37, 70`).
- `attackClass`: parsed from a `FILTER_GENERATED` line's text (`parseAttackClass`, `dashboardView.ts:50-53, 71`); for the first attack falls back to `activeAttack`.
- Record id = `anomaly.id`; `events = related.slice().reverse()` (oldest→newest) (`dashboardView.ts:80`).
- Related helper `selectAttackPackets` (`dashboardView.ts:85-95`) synthesizes packet rows from `packetCount` (not currently used in `App.tsx`).

Caveat for the report feature: because grouping is derived live from the client timeline (capped at 60 lines, `reducer.ts:161`), an incident's `events` reflect only what is still in the client buffer — older steps may be evicted.

# ESP32 OTA Filter Deployment — Research Report

**Bottom line up front:** For a real (non-theater) hackathon demo, ship **rule-data OTA** (option 2). The ESP32 cannot dynamically load compiled C, so full-image OTA would force a per-incident PlatformIO/ESP-IDF rebuild (30s–3min) into your autonomous loop — slow, fragile, and unconvincing to *watch*. Rule-data OTA lets the ESP pull a new filter over HTTP and enforce it live in **milliseconds**, which demos beautifully. Keep full-image OTA as the fallback story ("and for deep changes we can also push whole firmware"). Detail below.

---

## 1. Full-firmware-image OTA (filter compiled into the .bin)

### How it works — three ecosystems

**ESP-IDF `esp_https_ota` / `esp_ota_ops`** (the native path):
- High-level one-shot: build an `esp_http_client_config_t` pointing at your `.bin` URL, wrap in `esp_https_ota_config_t`, call `esp_https_ota(&amp;config)`. It downloads, writes to the inactive slot, verifies, and you reboot.
- Low-level (`esp_ota_ops.h`): `esp_ota_get_next_update_partition()` → `esp_ota_begin()` → `esp_ota_write()` in a download loop → `esp_ota_end()` → `esp_ota_set_boot_partition()` → `esp_restart()`. After reboot, run a self-check and call `esp_ota_mark_app_valid_cancel_rollback()`, else the bootloader rolls back. ([ESP-IDF OTA docs](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/ota.html))

**Arduino-ESP32** (fastest to write):
- `Update.h` is the low-level flash-writer. `HTTPUpdate` (`httpUpdate.update(client, url)`) is the "pull a .bin from a URL and apply it" convenience wrapper — exactly your backend-serves-bin flow. `ArduinoOTA` is push-from-IDE (not what you want). There is also an official `Update/examples/HTTPS_OTA_Update` sketch. ([Arduino-ESP32 OTA Web Update](https://docs.espressif.com/projects/arduino-esp32/en/latest/ota_web_update.html), [HTTPS_OTA_Update.ino](https://github.com/espressif/arduino-esp32/blob/master/libraries/Update/examples/HTTPS_OTA_Update/HTTPS_OTA_Update.ino), [Random Nerd OTA guide](https://randomnerdtutorials.com/esp32-ota-over-the-air-arduino/))

**PlatformIO**: `upload_protocol = espota` does push-over-network at dev time; for autonomous pull you'd still use the Arduino/IDF code above. PlatformIO's role in your loop is the **build**, not the transport.

### Partition requirements (same across all three)
- **At least two OTA app slots** (`ota_0`, `ota_1`) + an **`otadata`** partition holding the `ota_seq` boot pointer. New image is written to the *inactive* slot; `otadata` is flipped only after verification; the previous slot stays as rollback. ([ESP-IDF OTA docs](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/ota.html))
- **Min flash:** two app copies + otadata + nvs realistically needs **4 MB flash** (the standard on virtually every ESP32/ESP32-S3 devkit). 2 MB parts can't comfortably hold dual OTA slots.

### Backend-serves-.bin flow (exact)
1. Backend compiles firmware embedding the new `block_frame()` → produces `firmware.bin`.
2. Backend exposes `GET /firmware/latest.bin` (+ optionally a JSON manifest with version/sha256 — see [esp32HttpJsonOTA](https://github.com/mero20j1/esp32HttpJsonOTA)).
3. ESP polls the manifest (or gets a WS "deploy" nudge), calls `httpUpdate.update(client, "http://backend/firmware/latest.bin")` (Arduino) or `esp_https_ota(&amp;cfg)` (IDF).
4. Device writes inactive slot, verifies, flips otadata, reboots into new firmware, self-validates, cancels rollback. Total transport+reboot ≈ **5–15 s** over WiFi.

### Feasibility of building the .bin per-deploy in the loop — the problem
- **Build time is the killer.** Community reports: ESP32 clean builds ~**23 s** in a trimmed project up to **~180 s** (2–3 min) for typical projects; incremental one-line edits still often trigger **2–3 min** recompiles due to the Library Dependency Finder scanning headers. ([PlatformIO slow-build thread](https://community.platformio.org/t/scanning-dependencies-and-build-time-is-slow/26985), [insane compile times thread](https://community.platformio.org/t/esp32-insane-compile-times-everytime/22889))
- Headless invocation is trivial (`pio run` / `idf.py build`), so automation isn't the blocker — **latency is**. A demo where the "AI deploys a defense" and then you wait 90 seconds staring at a compiler is anti-climactic, and any toolchain hiccup (a missing include, a warning-as-error) fails the whole autonomous loop live on stage.
- Verdict: **technically real, but hackathon-hostile.** Only worth it if the filter genuinely must be C-in-firmware. It isn't (see §2).

## 2. Rule-data OTA — no recompile (the practical winner)

Firmware ships **once** with a fixed, tested interpreter. The "filter" is **data** the device fetches over HTTP and applies live. This is a well-trodden ESP32 pattern: poll a REST endpoint, get JSON config, apply at runtime, no reflash. ([Exploring IoT: JSON config over REST](https://richardscoding.wordpress.com/2021/08/21/json-config-files-using-rest-and-express/), [esp-fetch](https://github.com/ESPToolKit/esp-fetch), [ESP32 runtime config forum](https://esp32.com/viewtopic.php?t=5653))

### Rule schema (minimal, safe, 802.11-aware)
A filter = an ordered list of match rules; a frame is dropped if **any** rule matches (OR semantics; add `all`/`any` per rule for AND). Each rule is byte-offset/mask/value matching — expressive enough for frame-control type/subtype and address fields, and impossible to make Turing-complete (so it can't hang the RX path).

```json
{
  "filter_version": 7,
  "default": "pass",
  "rules": [
    { "name": "drop_deauth",
      "match": [
        { "offset": 0, "mask": "0xFC", "value": "0xC0" }   // FC: type=mgmt(00), subtype=deauth(1100)
      ] },
    { "name": "drop_spoofed_bssid",
      "match": [
        { "offset": 0,  "mask": "0x0C", "value": "0x00" },  // mgmt frame
        { "offset": 16, "mask": "0xFF", "value": "0xDE" },  // BSSID byte[0]
        { "offset": 17, "mask": "0xFF", "value": "0xAD" }
      ] }
  ]
}
```

### Per-frame eval loop (runs inside the promiscuous RX callback)
```c
// rules[] parsed once at fetch time into a flat fixed-size array (no malloc in RX path)
bool block_frame(const uint8_t *buf, size_t len) {
    for (int r = 0; r &lt; g_rule_count; r++) {
        const rule_t *rule = &amp;g_rules[r];
        bool matched = true;
        for (int m = 0; m &lt; rule-&gt;n; m++) {
            const cond_t *c = &amp;rule-&gt;cond[m];
            if (c-&gt;offset &gt;= len) { matched = false; break; }  // bounds check = safety
            if ((buf[c-&gt;offset] &amp; c-&gt;mask) != c-&gt;value) { matched = false; break; }
        }
        if (matched) return true;   // drop
    }
    return false;                    // pass
}
```
Note this is **the same signature** as your backend `block_frame(const uint8_t*, size_t)` — the interpreter *is* a `block_frame`, just table-driven. Bounds-checking every offset against `len` is the one safety rule that matters (a bad rule from the agent must never read OOB).

### Transport
ESP polls `GET /filter/current.json` (or receives a WS deploy event → then fetches), parses with ArduinoJson / cJSON into `g_rules`, atomically swaps the pointer. **Apply latency: milliseconds.** Version field lets the device confirm-back which filter it's enforcing (great for the dashboard).

### AI emits BOTH C and rule — keeping them equivalent
Yes, and this is the elegant part for your architecture:
- Agent emits the **C `block_frame`** → backend oracle compiles with `clang` and replay-tests against held-out fixtures (your authoritative gate, per AGENTS.md §5).
- Agent emits the **equivalent rule JSON** → gets pushed to the ESP.
- **Equivalence strategy (pick one, in order of rigor):**
  1. **Generate rule as ground truth, C as a view of it.** Have the agent emit the rule JSON, then mechanically transpile rule→C (trivial codegen) so the C the oracle tests is *provably* the rule. This makes them equivalent by construction — strongly recommended.
  2. If the agent writes C freely, run the oracle **twice**: once on the compiled C, once on a tiny host-side reimplementation of the rule interpreter fed the same JSON, over the same fixtures. Deploy the rule only if both produce identical drop/pass verdicts on every fixture. This turns "are they equivalent?" into a test the oracle already knows how to run.
- Either way the oracle stays authoritative and no human is in the loop — consistent with your autonomy rule (§6).

## 3. On-device enforcement reality (be honest about the RF physics)

**You cannot drop other stations' frames.** Promiscuous/monitor mode is a **receive-only** radio mode: `esp_wifi_set_promiscuous(true)` tells the MAC to hand *all* on-channel frames to your callback instead of filtering to your MAC. The frames have already been received by every other radio in range — there is no "intercept and discard" a defender can do to traffic between two *other* devices. Dropping is meaningful only for frames destined **to your own device/AP**. ([ESP32-Deauther promiscuous mode](https://deepwiki.com/tesa-klebeband/ESP32-Deauther-ArduinoIDE/6.1-promiscuous-mode-operation), [HackMag ESP32 sniffer](https://hackmag.com/security/esp32-sniffer), [what is monitor mode](https://infishark.com/blogs/learn/what-is-monitor-mode-how-wifi-packet-capture-actually-works))

So `block_frame()` returning `true` means different things depending on role. What a defender ESP can **realistically DO** with a "block" decision:

1. **Detect + log + alert (always honest).** The filter classifies the sniffed frame as malicious → device reports the incident (WS event to your dashboard). This is genuinely useful and 100% real — it's what real ESP32 IDS projects do (e.g. detecting deauth floods). ([Zenodo: ESP32 deauth-detection monitoring system](https://zenodo.org/records/19466381))
2. **Act as the AP and filter its OWN clients.** If the ESP is itself the softAP, it *can* enforce: refuse association, kick a client, ignore frames from a blacklisted MAC. Here "block" is real enforcement because the traffic is addressed to it.
3. **Active RF countermeasures (deauth) — legally and technically constrained.** Sending deauth to knock an attacker off is possible but: (a) Espressif's `esp_wifi_80211_tx()` **silently blocks** deauth/disassoc frame types (FC starting 0xC0/0xA0) — you'd need the well-known "WSL bypasser" hack used by deauther projects to inject them; (b) it's a jamming/DoS technique itself, ethically/legally dubious to demo; (c) **802.11w / PMF** makes modern clients immune to spoofed deauth anyway. ([esp_wifi_80211_tx frame-type restriction](https://gist.github.com/brainstorm/24e843ae0295ee1e41dff47c5b43a02c), [ESP32 penetration tool WSL bypasser](https://risinek.github.io/esp32-wifi-penetration-tool/main/), [ESP-IDF Wi-Fi security / PMF](https://docs.espressif.com/projects/esp-idf/en/v5.0.3/esp32/api-guides/wifi-security.html), [Deauther32 ESP32-S3 study](https://www.mdpi.com/1424-8220/26/11/3287))

**Honest framing for the pitch:** the sniffer's job is **detect + classify**; the defender's *enforceable* action is at the AP boundary (drop/ban its own clients) plus alerting. Don't claim the ESP "drops attacker traffic mid-air" — that's physically false and a sharp judge will catch it. "The device enforces the filter on frames it is responsible for, and instantly flags everything else" is both true and impressive.

## 4. Recommendation for a 5-minute pitch (ranked convincingness-vs-effort)

**Winner: (2) Rule-data OTA.** Because the ESP32 cannot dynamically load compiled C, and rebuilding+reflashing full firmware per incident is slow (30s–3min) and brittle on stage, rule-data OTA is the *only* option that delivers a live, watchable, sub-second "AI generates defense → device enforces it" loop — while your backend oracle still verifies the equivalent C. It's real, it's fast, and it maps cleanly onto your existing agent→oracle→deploy architecture.

**Effort breakdown for the recommended path (~1 day):**

**Demo narrative that's fully real:** anomaly sniffed → agent writes C `block_frame` + equivalent rule → oracle compiles the C with clang and replay-tests held-out fixtures → on pass, rule JSON pushed to ESP over HTTP → device swaps filter in ms and echoes back "enforcing v7" → dashboard shows the new class of frame now being dropped/flagged. No human, no reflash, no 2-minute compile, nothing faked.

## Filter-push reality (directly answers your purpose)

The "push a Devin-generated filter" mechanism already exists — **but it runs on a Python software node, not on the ESP32.**

- Backend publishes filters as **C source** at `GET /firmware/{node_id}` → `FirmwarePayload{ fw_version, filter_c_code, attack_class, sample_frames }` (`backend/app/main.py:118-131`; model `backend/app/models.py:145-152`). The docstring calls it "the real deployed filter for a node to pull, compile, and load" (`main.py:120`).
- The consumer is `backend/app/node_agent.py` — a **host Python process**, not firmware. It pulls the filter (`GET /firmware/{node_id}`, `:166`), **compiles it with `clang -shared -fPIC -O2` into a `.so`** (`_compile_shared`, `:59-75`), `dlopen`s it via `ctypes.CDLL` (`_load_block_frame`, `:78-89`), runs frames through `bool block_frame(const uint8_t*, size_t)`, and reports counts to `POST /enforcement` (`:175-183`). The oracle harness (`backend/oracle/harness.c:28,72`) uses the identical `block_frame` contract on held-out fixtures.
- The ESP sniffer firmware has **no counterpart**: it only forwards captured `frame_hex` to `/ingest` and always reports `"blocked":0` (`esp-sniffer-demo/src/main.cpp:201`). It cannot load `filter_c_code`, has no compiler, no OTA, and no interpreter.

**Bottom line for the hackathon decision:**
1. *Full recompiled firmware image over OTA to a real ESP32* — **not feasible as-is.** Zero OTA code exists; you'd have to add `ArduinoOTA`/`esp_https_ota` + a pull/apply loop from scratch. The partition tables (default_16MB.csv on the S3, default.csv on the classic boards) do already carry ota_0/ota_1 slots, so the flash layout wouldn't block you — the missing piece is entirely firmware code (plus a firmware-image endpoint; the backend only serves C *source* today).
2. *Filter as data the firmware interprets* — **also not feasible without new firmware**, because no ESP firmware contains any rule interpreter or `block_frame` runtime; that logic lives only in backend Python (`node_agent.py`) and as an unimplemented "signed policy manifest" proposal in `docs/ESP_ARCHITECTURE_REVIEW.md:114-139`. The C-source-over-HTTP model (`/firmware/{node_id}`) assumes an off-device compiler and `dlopen`, which an ESP32 cannot do.

The realistic hackathon path that matches what's already built is the **software enforcement node** (`python -m app.node_agent --backend URL --node esp-sw-01`, `node_agent.py:142-205`): Devin writes `block_frame`, the oracle verifies it on held-out captures, the node compiles+loads it live. Making a *physical* ESP32 do this would require net-new OTA-or-interpreter firmware that does not exist in any of the four projects today.</result>
